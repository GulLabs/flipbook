## Findings (new or under-specified relative to the inventory)

### BH-1 — Failed image with `complete === true` never stops the spinner

- **Where:** `packages/core/src/Page/ImagePage.ts:176-183`
- **Failure a user sees:** A 404 (or decode failure) that the browser has already
  settled before `load()` runs leaves the leaf on the loader arc forever. The
  book looks “still loading” on a page that will never arrive.
- **Why:** `load()` correctly treats `complete && naturalWidth === 0` as not
  loaded, but then **falls through** without returning and without attaching
  `onerror`. It only assigns `onload`, which will not fire again for a settled
  failure. Cached/failed images hit this path; slow 404s that error after
  `load()` also never get an `onerror` handler at all.
- **Related inventory:** A4 (spinner forever on 404) — this is a concrete second
  route into the same symptom, not just the missing-`onerror` case.
- **Suggested fix (for the Phase 2 owner):** attach `onerror` before any `src`
  mutation; on both the `complete && naturalWidth === 0` branch and `onerror`,
  set a `failed` flag, stop the loader, paint paper (+ glyph per ADR), emit
  `imageError` once per attempt.

### BH-2 — `onload` marks the page loaded without checking `naturalWidth`

- **Where:** `packages/core/src/Page/ImagePage.ts:181-183`
- **Failure a user sees:** Rare, but a decode that fires `load` with a zero-size
  bitmap is drawn as a successful page (empty `drawImage`) instead of the error
  path. Same leaf can look blank while sibling pages look fine.
- **Why:** The `complete` branch documents that `naturalWidth` is the real
  signal; the `onload` branch ignores it and sets `isLoad = true` unconditionally.
- **Related inventory:** A4 / error contract.

### BH-3 — Stretch-to-leaf is the only fit path (A3 still live)

- **Where:** `packages/core/src/Page/ImagePage.ts:100` and `:127`
  (`ctx.drawImage(this.image, …, pageWidth, pageHeight)`).
- **Failure a user sees:** Pre-rendered 2:3 picture-book pages in a 4:3 leaf are
  distorted; folios baked into the JPEG shear. The downstream reader already
  asks for `object-contain`.
- **Status:** KNOWN as A3. Confirmed still present; e2e `canvas-phase2.spec.ts`
  encodes the contain/cover contract and skips until `imageFit` lands.

### BH-4 — No blank-leaf representation

- **Where:** `packages/core/src/Collection/ImagePageCollection.ts` (constructor
  takes `string[]` only); `canvas-loader.ts:11`.
- **Failure a user sees:** A pad / inside-cover leaf cannot be expressed without
  shipping a 1×1 transparent PNG hack, which then hits G2 read-through unless
  paper is perfect.
- **Status:** Scope resolved in ADR 0001 (images + blank only). Not implemented.

### BH-5 — `loadFromImages` still typed and implemented as `string[]`

- **Where:** `packages/core/src/PageFlip.ts` (`loadFromImages(imagesHref: string[])`),
  `packages/core/src/index.ts` (no `ImagePageSource` export).
- **Failure a user sees:** Required `alt` cannot be expressed; bare strings are
  the only API; README still shows `loadFromImages(['page1.jpg', …])` with no
  `alt`. React `ImageFlipBook` therefore tries descriptors and falls back.
- **Status:** ADR Decision 1; Phase 2 not landed. React binding and the vanilla
  demo are written against the ADR and degrade on purpose.

### BH-6 — Incomplete `isTemporaryCopy` → `origin` rename (in-flight WIP)

- **Where:** `packages/core/src/Page/ImagePage.ts:221` still reads
  `this.isTemporaryCopy` after the field was renamed to `origin` (constructor
  ~lines 58–72, `drawState` ~80).
- **Failure a user sees:** `pnpm typecheck` fails across the monorepo
  (`Property 'isTemporaryCopy' does not exist`). At runtime, if anything
  reached `dispose()` on a temporary copy, it would throw before marking the
  copy spent.
- **Note:** Observed as concurrent uncommitted work from another agent. Not
  patched here (core hard boundary). The owning agent needs
  `if (this.origin !== null)` (or equivalent) on the dispose path.

## API ergonomics finding (from writing the examples)

Calling the **intended** ADR shape from a vanilla demo is fine: one
`ImagePageSource[]`, required `alt`, optional `fit`/`inset`.

What feels awkward **today** is the dual path every caller needs until Phase 2
lands:

```ts
try {
  await book.loadFromImages(descriptors);
} catch {
  await book.loadFromImages(descriptors.map((d) => d.src));
}
```

That is not an ADR problem; it is the cost of shipping examples ahead of the
engine. Once `loadFromImages(readonly ImagePageSource[])` is the only signature,
delete the fallback. Do **not** re-introduce a bare-string overload to make the
fallback permanent (ADR Decision 1).
